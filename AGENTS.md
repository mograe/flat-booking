# Flat Booking

- Telegram-адаптер отвечает за обработку обновлений, навигацию и локализацию. Сервисы реализуют правила без импорта Aiogram. Репозитории и модели отвечают за хранение.
- Используйте аннотации типов, snake_case для функций и полей, PascalCase для классов. Пользовательские сообщения пишите по-русски.
- Проверяйте роль и доступ к записи в сервисах. В журнале фиксируйте бизнес-события после успешной записи и ошибки с безопасным контекстом. Не записывайте токены, данные профилей, Telegram ID, комментарии и тексты сообщений. SQLAlchemy по умолчанию журналирует с уровня `WARNING`. При отладке скрывайте значения параметров SQL.
- Определяйте доступ участника по роли и блокировке пользователя в SQLite. Используйте Telegram User ID для идентификации. Проверяйте актуальные права в middleware на каждом защищённом действии и в сервисах. Заполняйте белый список из `WHITELIST_IDS` один раз на базу. Отзыв доступа сохраняет бронирования и профиль. Административные изменения списка фиксируйте в `AuditLog`.
- Используйте полуоткрытые интервалы и UTC. Проверку пересечения и изменение интервала выполняйте под BEGIN IMMEDIATE. Перенос должен сохранять исходный интервал при ошибке.
- Применяйте настроенные границы длительности ко всем ролям. Верхний предел одного бронирования составляет 1440 минут. Проверяйте доступность полного интервала, включая следующие даты. В расписании отображайте пересечение с местными сутками.
- Проверяйте очередь уведомлений и завершившиеся бронирования отдельными задачами с настраиваемыми интервалами. По умолчанию это 30 и 60 секунд соответственно. Обеспечивайте один запуск каждой задачи одновременно в процессе, открывайте транзакцию записи только при наличии работы и завершайте её до обращения к Telegram. Доставляйте просроченные напоминания до начала бронирования.
- При изменении схемы добавляйте явную миграцию Alembic. Тестируйте миграции на временной базе. Конкурентные тесты используют файловую SQLite и отдельные соединения.
- Тесты должны работать без Telegram API. При изменении правил добавляйте проверки граничных условий.
- Команды проверки: `uv run ruff check .`, `uv run ruff format --check .`, `uv run pytest`, `uv run alembic check` на мигрированной базе.

## Работа с Git

- Основная стабильная ветка проекта — `main`.
- Для каждого существенного изменения создавайте отдельную feature-ветку.
- Оформляйте сообщения коммитов по Conventional Commits.
- Перед созданием коммита запускайте `uv run pytest`, `uv run ruff check .` и `uv run ruff format --check .`.
- Перед коммитом просматривайте `git diff` и `git diff --staged`.
- Не добавляйте в Git секреты, файлы и значения переменных окружения, рабочую базу данных и резервные копии.
- Не используйте `git reset --hard`, `git clean -fd` и принудительную отправку изменений.
- Не перезаписывайте историю Git.
- Не объединяйте ветки без разрешения пользователя.
- Не отправляйте изменения в удалённый репозиторий без разрешения пользователя.
- По завершении задачи предлагайте сообщение коммита и приводите список внесённых изменений.
